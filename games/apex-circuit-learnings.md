# Apex Circuit 開発の気づき

このドキュメントは、`games/apex-circuit.html` を開発した際の成功例・失敗例・改善策を、今後のブラウザゲーム制作に再利用するためのメモです。

## うまくいった点

### 1. 最初から遊べる最小構成を作った

Three.jsをCDNから読み込み、HTML 1ファイルを中心に、タイトル・カウントダウン・レース・結果までを早い段階で動かした。先にゲームループを成立させたことで、後からAI、演出、音、ステージ進行を追加しやすかった。

### 2. モバイル操作を単純化した

操作を「浮遊型ジョイスティック1つ」に絞ったことで、画面を見ながら直感的に操作できた。ジョイスティックは固定表示ではなく、指を置いた場所に出す方式にすると、左右どちらの手でも使いやすい。

重要な入力設計:

- 縦入力: 前進・ブレーキ
- 横入力: ステアリング
- 横入力が強いときは縦入力の影響を弱める
- デッドゾーンを設け、指の微細な揺れを無視する
- `pointercapture` と `pointercancel` で指離れ・割り込みを確実に処理する

### 3. 生成画像をUIの印象づくりに使った

キービジュアルと路面テクスチャを生成し、タイトル画面とコースに利用した。ローポリの3D表現でも、最初に表示されるビジュアルの品質を上げるとゲーム全体の印象が大きく向上する。

### 4. 固定タイムステップを導入した

`requestAnimationFrame` の経過時間をそのまま物理計算に使うと、端末負荷やブラウザのフレーム落ちで挙動が変わる。1/60秒単位の固定ステップと、1フレームあたりの最大ステップ数を使うことで、端末差を小さくできた。

### 5. コース点の間を補間した

コース上の整数インデックスだけを参照すると、車体とカメラが点から点へ飛び、カクカクして見える。現在位置と次のコース点を線形補間し、接線も補間して車体の向きとカメラを滑らかにした。

## 問題になった点と改善策

### 1. 順位を現在位置だけで判定してはいけない

結果画面で、全車を`lap * コース長 + progress`だけで並べたところ、ゴール後の位置関係によって順位が変わる問題が起きた。

改善策:

- ゴールした車には`finished`と`finishTime`を記録する
- 完走車同士はゴール時刻順に並べる
- 未完走車はスタートライン基準の累積走行距離で並べる
- 結果表示用の順位と、レース中HUDの順位計算を同じ基準にする

### 2. 周回数をスタートライン通過だけで増やしてはいけない

後方グリッドの車をコースの反対側に配置した状態で、チェックポイント0の通過を周回完了として扱った。その結果、スタート直後に1周したことになる車が発生した。

改善策:

- レース開始時にスタートラインからの相対距離を設定する
- 車が進んだ距離を`raceDistance`として累積する
- ゴール条件を`raceDistance >= laps * trackLength`にする
- 周回表示も累積距離から計算する
- チェックポイントは不正な逆走防止やコース進行確認に使い、ゴール判定の唯一の根拠にはしない

### 3. 見た目の車体位置と順位用の位置を分けない

見た目はコース上の点と横ずれから計算し、順位は別の簡易値から計算すると、プレイヤーが見た追い抜きと結果順位が一致しなくなる。レースの基準となる距離を1つ持ち、表示・HUD・結果のすべてで共有する。

### 4. UIパネルの固定幅で画面外にはみ出した

`width: min(560px, 94vw)`と画面のpaddingを組み合わせると、グリッドの内側幅よりパネルが大きくなる場合がある。スマートフォンでは右側へ寄ったように見えた。

改善策:

```css
.screen { padding: 16px; min-width: 0; }
.panel { width: min(560px, calc(100vw - 32px)); min-width: 0; }
```

`100vw`だけでなく、画面の内側余白を引いた値で最大幅を決める。390px、590pxなど実際の端末幅で矩形を確認する。

### 5. 操作UIを増やしすぎない

ジョイスティックに加えて画面上の十字キーも追加したが、ユーザーの意図は「操作をシンプルに保つ」ことだった。モバイルはジョイスティック、PCはキーボード矢印キーというように、入力デバイスごとに役割を分けた方が画面がきれいになる。

## 今後の標準設計

### レース状態

車ごとに最低限、次の値を持つ。

```js
{
  progress,       // コース上の表示位置（ループする）
  raceDistance,   // スタートライン基準の累積距離（順位の基準）
  lap,
  finished,
  finishTime,
  lateral,        // コース中央からの横ずれ
  speed
}
```

`progress`は描画用、`raceDistance`は競技ルール用と明確に分ける。

### 車体表示

コース点は次の点との間を補間する。

```js
const i = Math.floor(progress);
const fraction = progress - i;
const position = center[i].clone().lerp(center[(i + 1) % N], fraction);
```

向きも隣接点の接線を補間して求める。カメラは車体位置を直接追いかけず、`lerp`で遅れて追従させる。

### AI難易度

序盤からプレイヤーを圧倒しない。初期ステージはAI速度を低めにし、上位入賞で次ステージへ進める。難易度は速度だけでなく、次も段階的に調整する。

- 最高速度
- コーナーでの減速率
- ミスの頻度
- ライン取りの精度
- オーバーテイクの積極性

### テスト

見た目だけでなく、次を自動テストする。

- HTML内のゲームフローと入力要素
- JavaScriptの構文
- 周回・チェックポイント・ゴール条件
- 完走時刻による順位
- スタート位置が異なる車の累積距離
- パネルのviewport内サイズ
- 生成画像の存在とPNG形式
- 既存ゲームへのリンクや共通ページへの影響

最後に、実機またはブラウザ自動操作で以下を確認する。

1. 起動画面が中央に収まる
2. レース開始後に車が静止画のまま残らない
3. ジョイスティックを離すと入力が解除される
4. 矢印キーで加速・制動・操舵できる
5. 見た目の追い抜きとHUD・結果順位が一致する

## まとめ

ブラウザの3Dレースゲームでは、見た目の補間と競技ルールの距離計算を別々に考えることが重要。特に「コース上の表示位置」と「スタートからの累積距離」を混同しないこと、順位をゴール時刻で確定すること、モバイル画面の内側幅を考慮してUIを設計することが、今回の最も重要な学びだった。
